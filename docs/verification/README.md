# Foundry 画面検証 / Browser verification

実際の Foundry VTT にブラウザーで入室し、シートや判定を操作する検証スクリプト。
`npm test` には含まれない。日付ごとのフォルダーに、スクリプトと結果の記録を置く。

## 準備

- Foundry を起動し、Sinless のワールド(既定 `sinless-test`)を起動する。
  起動していなければ `lib.mjs` の `launchWorld()` で起動できる。
- Gamemaster ユーザーにパスワードがないこと。
- Playwright はこのプロジェクトの依存に含めていない。手元の Playwright を指定する:

```sh
export SINLESS_PLAYWRIGHT=/path/to/node_modules/playwright/index.mjs
export SINLESS_FOUNDRY_URL=http://localhost:30000   # 省略時の既定値
```

## npm から実行

```sh
npm run verify -- list                 # 一覧
npm run verify -- batch player         # 複数指定は順に実行
npm run verify -- all --relaunch       # ワールドを再起動してから全部
```

- 名前: `sweep-ja`、`sweep-en`、`player`、`permissions`、`help-window`、`sheet-actions`、`keyboard`、`keyboard-dialogs`、`keyboard-apps`、`color-independence`、`contrast`、`non-text-contrast`、`text-resize`、`text-spacing`、`reflow`、`focus-visibility`、`target-size`、`batch`、`magic`、`samples`、`all`(この 20 本を順に実行)。
- 起動中のワールドがなければ `--world`(既定 `sinless-test`)を起動する。`--no-launch` で起動しない。
- 開始前に、ブラウザーが読み込んでいる system のバージョンと `system.json` を比べ、違えば警告する。
  `/api/status` の値は古いことがあるため使わない。`--relaunch` でワールドを再起動すると、Foundry がマニフェストを読み直す。
- アクティブなシーンがなく、キャンバスを使う `magic`・`player`・`help-window` が含まれていれば、開始せずに終了コード 1 で止まる(シーンを有効にしてから実行する)。
- 出力は `--out`(既定 `<tmp>/sinless-verify/<日時>`)の下の `<名前>/`。最後に各スクリプトの成否と所要時間を表示し、1 本でも失敗すれば終了コード 1。
- macOS では実行中だけ `caffeinate -i` でアイドルスリープを止める(スリープすると接続が切れ、シートがタイムアウトする)。
- 全部で約 5 分(2026-11-07、macOS)。以前は約 45 分かかっていた。headless Chromium はゲームキャンバスの WebGL をソフトウェアで描き、そのあいだページが塞がるため、サーバーの応答を受け取るたびに約 300 ms 待っていた。いまは macOS では GPU(Metal)で描き、総当たりではキャンバスを切っている。
- `npm run check` には含まれない。

## 入力欄のアクセシビリティ検証

`keyboard`・`keyboard-apps`・`keyboard-dialogs` は `input-accessibility.mjs` で Chromium のアクセシビリティツリーを読み、表示中の入力欄に名前があること、明示した名前が反映されること、チェック・選択・無効状態が正しく公開されることを確認する。リッチテキスト欄はキーボードで編集を開始し、名前のある複数行テキスト欄として公開され、保存後に編集ボタンへ戻ることも確認する。

`SINLESS_VERIFY_LANGUAGE=en` または `ja` を指定すると、検証用ブラウザーの言語を固定できる。ワールドや普段使うブラウザーの設定は変えない。これはブラウザーが支援技術へ渡す情報の検証であり、VoiceOver・NVDA の実際の音声読み上げの確認は含まない。

## 色に頼らない状態表示の検証

`color-independence` は、色で示している状態が文字や形でも伝わることを確かめる。判定カードのダイスは、成功・振り直しの別が Chromium のアクセシビリティツリーに文字として出ること、ブランドのリソース欄は名前の付いた 1 枚の画像として出て、ダメージは×、影響力は斜線で描かれることを確認する。続いて `forced-colors: active` を模擬し、状態モニターの埋まったマス、成功ダイス、リソースの印、オンの切り替えボタンの下線が消えないことを計算済みスタイルで確認する。Windows のハイコントラスト表示そのものは確認していない。オペレーションの発動中のアラート対応の読み上げ用テキストは、単体テストで確認している。

## 文字のコントラストの検証

`contrast` は、全種類のアクターシートの全タブ、ヘルプ・オペレーション・チェイスの画面、判定ダイアログ、判定カードで、文字のコントラストが WCAG 2.2 の AA 基準(通常の文字は 4.5:1、大きな文字は 3:1)を満たすことを、アプリケーションのダークテーマとライトテーマの両方で確認する。チャットカードの背景は羊皮紙の画像なので、背景色は計算済みスタイルからは取らない。文字を透明にしてスクリーンショットを撮り、各要素の範囲の画素の中央値を背景とする。文字色は計算済みの色に祖先の `opacity` を掛けたもの。入力欄の値とプレースホルダーも対象にし、無効の入力欄とアイコンは除く。スクロールで隠れた要素や、他の要素に覆われた要素は測らない。検証中に変えたテーマ設定は元に戻す。

## 文字以外のコントラストの検証

`non-text-contrast` は、操作部品と状態を示す図形が周囲と 3:1 以上のコントラストを持つこと(WCAG 2.2 の 1.4.11)を、アプリケーションのダークテーマとライトテーマの両方で確かめる。対象は入力欄・選択欄・チェックボックス・状態モニターのマス・リソースのマス・判定カードのダイスの境界と、アイコンだけのボタンのアイコン。範囲はサンプルアクターの全タブ(状態モニターを埋め、ブランドには損害と影響力のあるリソースを足す)、ヘルプ・オペレーション・チェイスの画面、判定ダイアログ、判定カード。

境界はスクリーンショットから読む(枠が `currentColor` のことがあるため文字は消さない)。各辺の中央半分で、縁から内側数ピクセルの中央値と、外側 1px の中央値を比べ、どれかの辺か塗りが 3:1 以上なら合格(下線だけの入力欄も識別できるため)。Foundry のチェックボックスは `::before` のグリフで描かれ、入力欄より大きいか、フォームグループの幅のブロックの先頭にあるため、付近の画素から背景と違う範囲を探してグリフの箱とする。アイコンは `contrast` と同じく、計算済みの色に祖先の `opacity` を掛け、アイコンを透明にした画面の中央値を背景とする。無効の部品は除く。

ヒートの星は、設定を変えるとチャットに投稿されるため、画面上で 2 つに `on` を付けて点灯時の色も測る。`SINLESS_NONTEXT_SHOTS=1` で、不合格のあった画面のスクリーンショットを出力先に保存する。修正前は、ダークテーマの入力欄・選択欄(Foundry の枠が透明で、塗りは 1.39:1)、状態モニターとリソースのマス、オフのチェックボックス、ライトテーマのオンのチェックボックス(羊皮紙の上のオレンジ 1.5:1)、オフの星(2.26:1)とオンの星(1.32:1)が 3:1 未満だった。検証後はテーマ・オペレーション・チェイスの設定を戻し、作ったアクターとメッセージを削除する。

## 文字の拡大の検証

`text-resize` は、文字を 200% に拡大しても内容が失われないこと(WCAG 2.2 の 1.4.4)を確かめる。Foundry の文字サイズ設定は最大の 10 でルートの文字サイズが 16px から 32px になるが、ウィンドウの幅は変わらない。この設定で、全種類のアクターシートの全タブ、アイテムシート、ヘルプ・オペレーション・チェイスの画面、判定ダイアログを既定の大きさで開き、次のどれもないことを確認する。

- 内容が横にはみ出して切れる。縦にはみ出すのにスクロールできない
- 文字が、自分や祖先の `overflow: hidden` で切れる
- 入力欄や選択欄が狭く、値が入りきらない
- 文字が 3 文字分より狭い列に押し込まれ、1 文字ずつ折り返す
- 文字が箱より高くなり、下にはみ出す(折り返したボタンの文字など)。フォントの高さが行の高さを超える分は除く

`SINLESS_TEXT_SCALE` で別の文字サイズ(1〜10)を、`SINLESS_TEXT_WIDTH` でシートの幅(px)を指定できる。例えば `SINLESS_TEXT_SCALE=5 SINLESS_TEXT_WIDTH=400` は、標準の文字サイズで狭くしたシート(1.4.10 のリフロー)を確かめる。`SINLESS_TEXT_SHOTS=1` で、問題のあった画面のスクリーンショットを出力先に保存する。検証後は文字サイズの設定を元に戻す。

レイアウトは CSS のコンテナークエリーで切り替えている。各ウィンドウの内容部分の幅を `rem` で測るので、文字の拡大とウィンドウの縮小のどちらでも同じ規則が働く。シートは 40rem 未満(標準の文字サイズで 640px)になると、ヘッダーを含めてシート全体がスクロールし、横に並んでいた行が折り返す。ダイアログとトラッカーは 24rem 未満で、見出しを入力欄の上に置く。

Foundry はボタンの高さを 2em に固定しているため、文字が折り返すとボタンの外にはみ出す。Sinless のウィンドウとチャットカードのボタンは高さを `auto` にして、折り返した分だけ高くなるようにしている(最小の高さは 2em のまま)。チャットカードの目標値は、幅が足りないと題の下に回る。

## 文字の間隔の検証

`text-spacing` は、利用者のスタイルで文字の間隔を広げても内容が失われないこと(WCAG 2.2 の 1.4.12)を確かめる。`text-resize` と同じスクリプトに引数 `spacing` を渡し、文字の大きさは変えずに、行の高さ 1.5、段落の後ろの間隔 2em、文字の間隔 0.12em、単語の間隔 0.16em のスタイルを全体に加える。同じ画面を開き、`text-resize` と同じ項目を確認する。スタイルが効いていることは、本文の行の高さ・文字の間隔・単語の間隔を読んで確かめる。選択欄や狭い列の文字幅の測定にも文字と単語の間隔を含める。検証後は、自分で作ったチャットメッセージだけを削除する。

日本語・英語での実行結果は [2026-11-08/text-spacing/README.md](2026-11-08/text-spacing/README.md) に記録している。

## 狭いシートの検証

`npm run verify -- reflow` は標準の文字サイズ（font scale 5）でアクターと武器のシートを幅320pxにし、`text-resize` と同じ内容の欠落を検査する。ヘルプ・オペレーション・チェイス・判定ダイアログとチャットカードも既定幅で確認する。ブラウザーのビューポート全体を320pxにする検証ではない。結果は `reflow.json` に出力する。日本語・英語の記録は [reflow/README.md](2026-11-08/reflow/README.md) を参照。

ブランドの残りアクション数、アクション一覧、リソースの操作欄は、内容領域が24rem以下になると縦に並ぶ。

## スクロール後のフォーカス検証

`keyboard` は `2026-11-08/focus-scroll.mjs` で、装備35件を持つキャラクターシートの末尾も検証する。通常幅800px、狭い幅320px、200%文字拡大（幅800px）の3条件で高さを500pxにし、末尾の携行ボタンをSpaceとEnterで切り替え、装備編集画面をEnterで開いて閉じる。各操作後に同じ対象へフォーカスが戻ること、実際にスクロールした状態であること、対象の中心が `elementFromPoint` でその対象か子要素に当たることを確認する。スクロール量が完全に同じであることや、枠の全周が見えることを保証する検証ではない。検証用アクターを削除し、文字サイズを含むUI設定を復元する。日本語・英語の結果は [focus-scroll/README.md](2026-11-08/focus-scroll/README.md) を参照。

## フォーカス枠の検証

`npm run verify -- focus-visibility` はキャラクターシートの名前・出自・ライフスタイル操作・作成ボタン・技能ランクの5例を、明暗のアプリケーションテーマで測定する。Tab操作の後に各対象へフォーカスを移し、`:focus-visible` と2px以上の実線枠を確認する。画面キャプチャから枠の上辺中央とその外側の画素を読み、コントラストが3:1以上であることを確認する。測定時は遷移アニメーションを止める。対象はサンプルであり、全画面の枠や遮蔽、WCAG全体への適合を確認する検証ではない。作成したアクターを削除し、UI設定を復元する。

Sinlessの入力欄・選択欄・テキスト欄・編集欄・操作リンクと、内容領域内のボタンは、テーマの主文字色で枠を描く。ウィンドウヘッダーのボタンはFoundry既存の枠を使う。

## 操作対象の大きさの検証

`target-size` は、クリックやタップの対象が 24×24 CSS ピクセル以上あること(WCAG 2.2 の 2.5.8)を確かめる。小さい対象でも、中心に置いた直径 24px の円が、ほかの対象にも、ほかの小さい対象の円にも重ならなければよい(間隔の例外)。チェックボックスや入力欄は、クリックできるラベルを含めた範囲で測る。文中のリンクは対象外(インラインの例外)。

サンプルのアクター(全種類のシートの全タブ)、全種類のアイテムシート、ヘルプ・オペレーション・チェイスの画面(アラート対応、進行中のチェイスと追手を入れた状態)、判定ダイアログ、チャットカードを開いて測る。`SINLESS_TARGET_SHOTS=1` で、各画面のスクリーンショットを出力先に保存する。検証後は、作ったアクターとチャットメッセージを消し、オペレーションとチェイスの設定を元に戻す。

状態モニターのマス、アイテムと効果の行の操作アイコン、ブランド特性、ライフスタイルの操作、チェイスの区間の増減は、`max(1.5rem, 24px)` 以上にしている。文字サイズを標準より小さくしても 24px を下回らない。

## チャットの後片付けの回帰検証

`npm run verify -- chat-cleanup` は `all` とは別に実行する追加の検証。`color-independence`・`contrast`・`target-size` を実際に動かし、それぞれが検証用カードを作った後、別の一時GMセッションから無関係なチャットを追加する。終了後に、そのチャットと実行前からあった全メッセージが残ることを確認する。3本それぞれの表示検証と、検証自身のカードの削除確認も通ることが必要。終了後は、この回帰検証が作ったチャットと一時ユーザーだけを削除する。

3本の後片付けは、開始後に増えた全チャットではなく、各検証が作ったカードのIDだけを削除する。アクターの残存確認も、名前の接頭辞ではなく作成したIDで行う。実行結果は [chat-cleanup/README.md](2026-11-08/chat-cleanup/README.md) を参照。

`npm run verify -- sample-chat-cleanup` はサンプル検証向けの追加検証。サンプルの最初の判定カードが作られた後、別ユーザーの投稿と実行GMと同じ作者IDの投稿を追加し、両方と既存チャットが残ることを確認する。`samples` の後片付けは開始後のメッセージのうち、検証用アクターの発言者ID、検証用シーン、または `flags.sinless.actorUuid` が検証用アクターに一致するものだけを削除する。アクター・シーン・戦闘・関連メッセージの残存も確認する。このコマンドも `all` の20本には含めない。結果は [sample-chat-cleanup/README.md](2026-11-08/sample-chat-cleanup/README.md) を参照。

## 共通ヘルパー [lib.mjs](lib.mjs)

- `joinGM({ user, viewport, browser, noCanvas })`: 入室して `game.ready` を待つ。`{ browser, page, logs }` を返す。
  `browser` を渡すと、起動済みのブラウザーに別のコンテキストで 2 つ目のセッションを足す(Foundry はセッションを Cookie で見分ける)。
  `noCanvas` はそのセッションのゲームキャンバスを切る。トークンを使わないスクリプト向け。
- `launchBrowser()`: headless Chromium を起動する。macOS では GPU で描く。
- `launchWorld(world)`: アクティブなワールドがなければ起動する。
- `relaunchWorld(world)`: ワールドを終了して起動し直す。
- `loadedVersions()`: ブラウザーから見た Foundry・system のバージョン、ワールド、言語、アクティブなシーン。
- `loadChromium()`: 上記の環境変数から Playwright を読み込む。

総当たりは、シートを `SINLESS_SWEEP_WORKERS`(既定 3)本のセッションに分けて並行に回す。
Foundry は 1 ユーザーにつき 1 セッションしか認めないため、2 本目以降は一時的な GM ユーザー(`SWEEP-<言語> GM <番号>`)で入室し、終了時に削除する。
アクターとその所持アイテムは同じセッションで順に回し、同じシートの再描画が重ならないようにする。

各スクリプトは作成したテスト用データを終了時に削除する。

`batch` は途中で止まっても次の実行で元に戻せるようにしている。前提データを作る前に、アクティブなシーンと Sinless の設定を `<tmp>/sinless-verify/batch-fixtures.json`(`SINLESS_FIXTURE_RECOVERY` で変更可)に書き、作るアクターと SMOKE Scene には `flags.sinless.verifyFixture` に実行 ID を付ける。正常に後片付けが済めばこのファイルを消す。強制終了やスリープで後片付けが走らなかった場合、次の `batch` が開始時にファイルを見つけ、次のものを削除してからシーンと設定を戻す。

- その実行 ID の付いたアクターとシーン
- 実行開始後に作られた `SMOKE ` で始まる名前のアクターと `Chase Pursuer`(各スクリプトが自分で作るもの)
- それらに関わる戦闘とチャット

ファイルに書かれたプロセスがまだ動いていれば、別の `batch` が実行中とみなして止まる。記録のない SMOKE データ(手で作ったもの、この仕組みより前に残ったもの)は自動では消さず、エラーで止まる。手で消すときは、SMOKE Scene がアクティブなシーンになっているので、消した後に元のシーンを有効にし直すこと。復旧でシーンを有効にしたクライアントには `Scene#active` が古いまま残ることがある(Foundry 14.365 で確認)ため、復旧後はページを読み込み直してから現状を記録する。
その後の起動で Foundry のログに `Deleted N orphaned embedded documents from the scenes database` と出るのは想定どおり。リンクしていないトークンの効果を外すと削除印が残り、Foundry はトークンやシーンを削除してもそれを消さず、起動時に掃除する。削除の順序では防げず、害はない(2026-11-07 確認)。
`2026-11-06/original/` は当時のスナップショットで、機械固有のパスを含むためそのままでは動かない。
`current/batch.mjs` は、読み込み時にそのパスを `lib.mjs` へ置き換えて実行する。
あわせて、スクリプト中の固定の待ち時間(`waitForTimeout`)を `SINLESS_BATCH_WAIT` 倍(既定 0.2)に縮める。ただし 500 ms(元の待ちがそれより短ければ元の値)は残す。ダイアログのボタンの直後の待ちは閉じるアニメーションも含むため、縮めすぎると読み取りが早すぎる。当時の待ち時間はソフトウェア描画の遅いキャンバスに合わせたもので、`1` にすると元に戻る。
